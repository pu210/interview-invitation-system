# 三日範圍與驗收矩陣

## P0｜三日內必須完成

| 情境 | 核心判斷 | 完成訊號 |
| --- | --- | --- |
| P0-01 104 正常邀約 | 有 104 履歷編號，可以進入邀約 | 建立一次邀約紀錄，狀態為 `INVITATION_ACCEPTED` |
| P0-02 非 104、無履歷編號 | 仍可用 candidateId 穩定識別 | 不因 resumeId 為空而拒絕，建立一次邀約紀錄 |
| P0-03 一邀未回後二邀 | 只在符合等待條件時發第二邀 | 只新增一筆 `SECOND_INVITATION` |
| P0-04 三個月內重複邀約 | 以固定時間判斷 90 天範圍 | 狀態為 `DUPLICATE_BLOCKED`，不建立信件 |
| P0-05 主管婉拒 | 停止下游處理 | 狀態為 `SUPERVISOR_REJECTED`，信件／日曆皆為 0 |
| P0-06 確認面試 | 以同一 operationId 防止重複 | 各建立一次模擬日曆、通知及 Drive 檔案，重跑不重複 |

## P1｜P0 全數通過後選做

- P1-01 候選人婉拒。
- P1-02 面試改期。
- P1-03 二面交由人工處理。

## P2｜只需提出設計與驗證策略

- P2-01 寄信失敗與安全重試。

## 明確排除

- 正式或測試 Google API、OAuth、Calendar、Drive、Gmail。
- 真實候選人、主管、Email、履歷或公司資源 ID。
- 正式資料遷移、正式觸發器與產品化權限模型。
- React、Angular、Vue 等額外前端框架。
- 完整招募系統或四十個工作表的重建。

## 每日產出

- Day 1：可啟動環境、六個 P0 流程圖、需求釐清表、未知問題。
- Day 2：選定語言的可操作 Demo、系統設計說明、六個 P0 的實作進度。
- Day 3：自動測試、精簡證據表、修正前後差異，以及正常／重複／婉拒三類 Demo。
